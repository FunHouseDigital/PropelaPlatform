# Bugfix Requirements Document

## Introduction

This bugfix addresses a production responsive-layout defect in the nurse create and edit interfaces. When a nurse form is taller than the available browser viewport, the primary persistence action at the bottom of the interface—`Create nurse` for creation or `Save changes` for editing—is not visible or reachable at normal browser zoom. A production user had to reduce browser zoom to 50% or less to reach the action.

For this bugfix, a **Supported_Viewport** is any viewport in the application's supported responsive range with a rendered width of at least 320 CSS pixels and a rendered height of at least 568 CSS pixels, including mobile layouts below 768 CSS pixels wide and desktop layouts at or above 768 CSS pixels wide. **Normal_Zoom** is the browser's default 100% zoom. A primary action is **Reachable** when the user can bring the complete enabled action into view and activate it through the interface's ordinary pointer, touch, scrolling, or keyboard interaction without reducing browser zoom, changing display scaling, or bypassing the form.

The bug condition C(X) is: a nurse create or edit interface is open in a Supported_Viewport at Normal_Zoom, and its rendered content is taller than the vertical space available to that interface. For inputs satisfying C(X), the corrected interface must keep its primary persistence action Reachable. For inputs not satisfying C(X), existing nurse, authentication, persistence, authorization, validation, accessibility, and correct responsive behavior must remain unchanged.

The previously reported production authentication issue is outside this bug condition and is verified fixed: Emily appears after a clean sign-in, Loyiso was created successfully, and Loyiso remained persisted across sign-out and sign-in. This bugfix must not regress those verified outcomes.

## Bug Analysis

### Current Behavior (Defect)

The defect occurs when the rendered nurse create or edit content exceeds the vertical space available to the active interface in a Supported_Viewport at Normal_Zoom.

1.1 WHEN an authorized user opens the nurse create interface at 100% browser zoom in a Supported_Viewport and the rendered create content overflows the vertical space available to the active interface, THEN the system places the complete enabled `Create nurse` action outside every attainable viewport position: pointer input cannot bring the complete action into view or activate it, touch input cannot bring the complete action into view or activate it, ordinary scrolling cannot bring the complete action into view, and keyboard input cannot focus or activate it.

1.2 WHEN an authorized user opens a nurse edit interface at 100% browser zoom in a Supported_Viewport and the rendered edit content overflows the vertical space available to the active interface, THEN the system places the complete enabled `Save changes` action outside every attainable viewport position: pointer input cannot bring the complete action into view or activate it, touch input cannot bring the complete action into view or activate it, ordinary scrolling cannot bring the complete action into view, and keyboard input cannot focus or activate it.

### Expected Behavior (Correct)

The complete create and edit workflows must remain operable at Normal_Zoom throughout the Supported_Viewport range.

2.1 WHEN an authorized user opens the nurse create interface at 100% browser zoom in a Supported_Viewport and the rendered create content overflows the interface's available height, THEN the system SHALL provide an ordinary scroll path from the first form content to a position where the complete `Create nurse` action is within the viewport, is not clipped, covered, or obscured by any interface element, and is activatable by each supported input method when enabled.

2.2 WHEN an authorized user opens a nurse edit interface at 100% browser zoom in a Supported_Viewport and the rendered edit content overflows the interface's available height, THEN the system SHALL provide an ordinary scroll path from the first form content to a position where the complete `Save changes` action is within the viewport, is not clipped, covered, or obscured by any interface element, and is activatable by each supported input method when enabled.

2.3 WHEN the viewport width or height is resized while an authorized user has a nurse create or edit interface open at 100% browser zoom and the resized viewport remains a Supported_Viewport, THEN the system SHALL preserve all entered values and provide an ordinary scroll path to a position where the complete applicable primary action is within the resized viewport, is not clipped, covered, or obscured by any interface element, and is activatable by each supported input method when enabled, without requiring the interface to be closed or browser zoom to be changed.

2.4 WHEN validation messages, error or failure notices, conflict content or controls, or expanded form sections increase the height of an open nurse create or edit interface at 100% browser zoom in a Supported_Viewport, THEN the system SHALL provide an ordinary scroll path through the expanded content to a position where the complete applicable primary action is within the viewport, is not clipped, covered, or obscured by any interface element, and is activatable by pointer, touch, and keyboard when enabled, while preserving its existing enabled or disabled state.

### Unchanged Behavior (Regression Prevention)

The correction is limited to visibility and reachability of nurse-form actions; it must not alter established workflow semantics or production data behavior.

3.1 WHEN a nurse create or edit interface is rendered in a Supported_Viewport at 100% browser zoom, THEN the system SHALL CONTINUE TO render each pre-existing heading, message, form field, secondary action, and primary action exactly once and in the same relative visual and DOM order; retain the mobile arrangement below 768 CSS pixels and desktop arrangement at or above 768 CSS pixels; retain the `Create nurse` and `Save changes` labels; and prevent clipping, overlap, or obscuration for content that fits within the available height.

3.2 WHEN a user opens, changes, validates, cancels, retries, or submits a nurse create or edit form, THEN the system SHALL CONTINUE TO initialize the same fields and values; isolate changes in the applicable draft until a server-confirmed submission succeeds; produce the same normalized and derived values from identical input; reject the same invalid input with the same field-level validation indication; focus the first invalid field; preserve every draft value after validation or submission rejection; and retain the same close, discard-confirmation, retry, and successful-submission outcomes.

3.3 WHEN a user operates a nurse create or edit interface using only a keyboard, THEN the system SHALL CONTINUE TO move Tab focus once through each enabled interactive control in visual order and Shift+Tab focus through those controls in reverse order; show a visible focus indicator; contain focus within an active modal; scroll the focused control into view; activate an enabled focused action with its supported activation key; retain the same Escape and Cancel outcomes for the same draft state; and restore focus to the invoking control when the interface closes.

3.4 WHERE Supabase-backed mode is enabled, WHEN a production browser context with no pre-existing session completes sign-in, authentication readiness confirms the resulting Supabase session is active, and the first nurse operation begins, THEN the system SHALL CONTINUE TO send that operation with the active session; display each server-confirmed nurse record returned under RLS exactly once, including Emily when Supabase returns Emily's record; and show a session-expiry indication only if Supabase reports the session absent, invalid, or expired before the operation completes.

3.5 WHERE Supabase-backed mode is enabled, WHEN the authorized production user signs out and signs in again and no authorized update or deletion of the server-persisted Loyiso record occurs between those events, THEN the system SHALL CONTINUE TO retrieve Loyiso from Supabase and display exactly one Loyiso record with the same server record identifier and persisted field values, without creating, duplicating, replacing, or reconstructing that record from client-held state.

3.6 WHERE Supabase-backed mode is enabled, WHEN any nurse create, read, update, Pipeline_Change, delete, refresh, conflict-resolution, retry, validation, or failure workflow completes, THEN the system SHALL CONTINUE TO add, replace, or remove shared nurse state only from a successful server-confirmed Supabase response; preserve the applicable draft and the complete last server-confirmed list and detail state after every rejected, failed, or conflicting result; identify the failure or conflict; and never substitute localStorage records or bundled sample nurses for server-confirmed state.

3.7 WHERE Supabase-backed mode is enabled, WHEN a nurse operation is requested, THEN the system SHALL CONTINUE TO wait until authentication readiness resolves to authenticated or unauthenticated before issuing a Supabase nurse request; use the public Supabase client and active session for authenticated requests; issue no request when no active session exists; expose and mutate only records permitted by RLS; and, after an RLS denial, return no denied data, apply no mutation, and retain the complete last server-confirmed state.

3.8 WHEN an authorized user performs a nurse create, update, Pipeline_Change, delete, retry, or conflict-resolution workflow, THEN the system SHALL CONTINUE TO issue a mutation only after the corresponding explicit action; accept state changes only from the successful server-returned result; preserve server-returned record identifiers and owner metadata; deduplicate repeated create attempts with the same create-draft identifier and values to one record; submit Base_Version for update, Pipeline_Change, and delete operations; replace accepted state only with the returned record and greater Version after a successful versioned update; remove a record only after successful delete or Already_Deleted; preserve the draft and last server-confirmed state after a version conflict; display the latest server record and applicable review, rebase, discard, reload, or keep-editing controls; and perform no automatic retry.

3.9 WHEN a nurse create, save, or delete operation is pending or returns a failed result, THEN the system SHALL CONTINUE TO preserve the applicable draft and displayed server-confirmed state; prevent a second request for the same operation while the first is pending; retain the primary action's enabled or disabled state for identical form values, permissions, and operation state; offer a manual Retry action only for a recoverable failure; offer conflict-resolution actions rather than unconditional retry for a conflict; and offer no Retry action while an authentication, permission, validation, or database-rule failure remains unresolved.

3.10 WHILE Supabase-backed mode is disabled, the system SHALL CONTINUE TO route nurse initialization, create, read, update, Pipeline_Change, delete, and refresh exclusively through the legacy localStorage implementation; seed and display the seven bundled sample nurses only under the pre-correction sample-seeding conditions; retain successfully persisted local nurse data after browser refresh; produce the same authentication outcome for the same user state; and issue zero Supabase nurse requests.

3.11 WHEN the current user lacks create or edit permission for nurses, THEN the system SHALL CONTINUE TO render the applicable `Create nurse` or `Save changes` action absent or disabled according to the same pre-correction permission result; prevent pointer, touch, keyboard, or programmatic activation from initiating a nurse mutation; keep that authorization result independent of action visibility, viewport position, or Reachability; and rely on RLS to reject every mutation not authorized for the active session without changing server-confirmed state.
