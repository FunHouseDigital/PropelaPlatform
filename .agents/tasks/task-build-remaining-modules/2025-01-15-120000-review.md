# Four Propela Ops modules: Dashboard, Cohort Manager, Acquisition Hub, Template Library

This change adds four complete UI modules to the Propela nurse management platform, each with its own route, server page, client component tree, mock data, Zustand store, and type definitions. The implementation follows the existing pattern established by the Nurses module: server components fetch data from `src/lib/data.ts`, pass it to `"use client"` component trees, and Zustand handles local view state (filters, search, active tab). All four modules are wired into the sidebar and the root route now redirects to `/dashboard`.

Watch for: all quick-action links in Dashboard point to `/nurses` regardless of intent (confirmed); `getStatusColor` and badge-color helpers are duplicated across 5+ files with no shared utility (confirmed); the `params` access pattern in dynamic route pages will break under Next.js 15 without `await` (likely).

## High-level view

The Dashboard page computes stats and pipeline data in its server component, deriving activity items from nurse `lastContacted` dates. The QuickActions section links every action to `/nurses` rather than routing to relevant filtered views or using distinct routes — "Send Reminders" and "Export Report" have no real target anywhere in the app.

The Cohort Manager is a card grid with a detail page per cohort. The data model embeds nurse summaries directly in each cohort rather than joining on IDs, which duplicates nurse state and will diverge from the nurse database as soon as real data lands.

The Acquisition Hub splits sources into four typed tabs plus a kanban-style outreach pipeline. The search and status filter state is shared across all source tabs, meaning switching tabs preserves a filter that may not apply to the new tab's data, producing a confusing empty state.

The Template Library introduces category and status filtering with a detail page that highlights `{{placeholder}}` tokens in template bodies. The "Create Template" button is rendered with full interactive styling but does nothing — a dead UI element that will confuse users in testing.

## Dashboard dead-end quick actions

The QuickActions component renders four cards, but every card's `href` is `/nurses`:

```tsx
{ label: "Review Applications", href: "/nurses", ... },
{ label: "Chase OET Results", href: "/nurses", ... },
{ label: "Send Reminders", href: "/nurses", ... },
{ label: "Export Report", href: "/nurses", ... },
```

"Send Reminders" and "Export Report" don't have real targets anywhere in the app. They should either link to the templates module / an export flow, or be rendered in a disabled state. Presenting them as navigable actions sets a user expectation the app can't fulfill.

## Cohort data model: embedded nurse summaries

The `Cohort` type contains a `nurses: CohortNurseSummary[]` array with denormalized fields (`fullName`, `pipelineStage`, `oetStatus`, `placementStatus`). When a nurse's stage changes in the nurse database, the cohort's embedded copy becomes stale unless explicitly synchronized. A join-on-ID approach via the data layer (`getNursesByCohort(ids)`) would avoid this divergence when transitioning to Prisma.

## Acquisition filter state leak across tabs

`useAcquisitionStore` holds a single `searchQuery` and `statusFilter` that persists across tab switches. If a user filters by "Inactive" on the Organisations tab, then switches to Events, the "Inactive" filter carries over. Since the Events tab may have no inactive sources, the user sees "No sources found." Reset filters on tab change:

```tsx
setActiveTab: (tab) => set({ activeTab: tab, searchQuery: '', statusFilter: '' }),
```

## Inert "Create Template" button

The button in `TemplateLibrary.tsx` has no `onClick` handler and no `disabled` attribute:

```tsx
<button className="flex items-center gap-2 rounded-lg bg-propela-purple px-4 py-2 ...">
  <Plus className="h-4 w-4" />
  Create Template
</button>
```

This looks fully interactive but does nothing on click. Add `disabled` with reduced opacity, or remove it until the create flow exists.

## Duplicated helper functions

`getStatusColor` appears in CohortCard.tsx, CohortDetail.tsx, TemplateCard.tsx, and TemplateDetail.tsx with slight variations. `getCategoryColor` is duplicated between TemplateCard and TemplateDetail. These should consolidate into a shared `src/lib/badge-colors.ts` to prevent drift as new statuses are added.

## Next.js params contract

Both `/cohorts/[id]/page.tsx` and `/templates/[id]/page.tsx` use:

```tsx
export default async function Page({ params }: { params: { id: string } }) {
  const item = await getById(params.id);
```

In Next.js 15, `params` becomes `Promise<{ id: string }>` and must be awaited. This won't break on Next.js 14 but will block an upgrade.

## Test coverage

There are no tests. The project relies on `pnpm build` + `pnpm lint` for verification. All filtering and data derivation logic lives in client components (TemplateLibrary's `useMemo`, SourceGrid's filter chain, Dashboard's stat computation) and is only exercised by manual browser testing. Not tested: filter combinations that produce empty results, cohort with zero budget allocated (division by zero is guarded but untested), templates with no tags, dashboard with zero nurses.
