# Nurse Database module for Propela Ops platform

A greenfield Next.js 14 App Router application implementing the Nurse Database module: a gallery view with search/filter/sort controls, a Kanban pipeline view with drag-and-drop stage transitions, and a per-nurse detail card with collapsible field sections and a live scorecard. The data layer uses mock data with a Prisma schema defined for future persistence. The build and lint pass clean.

Watch for: Two different scoring formulas exist for the same concept (confirmed), the Next Action dropdown options are completely decoupled from the `NextAction` type used elsewhere (confirmed), and the Pipeline view's local state diverges from the parent filter state on prop changes (confirmed).

## High-level view

The scorecard calculation logic is duplicated between `nurse-utils.ts` (used on gallery cards) and `NurseCardDetail.tsx` (used on the detail page), and the two implementations use different formulas. The gallery view computes `finalScore` as a raw sum out of 80, while the detail view computes a weighted average out of 10. A nurse that appears as "Tier 1" on one screen could appear as "Tier 2 Development" on the other.

The `NextActionDropdown` in the detail card presents a set of options (e.g., "Needs: Chase CV, then scoring") that have zero overlap with the `NextAction` union type defined in `types/nurse.ts` (e.g., "Request CV", "Review CV"). The dropdown writes its selection through a server action, but any consumer that reads `nurse.nextAction` expecting the typed enum will get an unrecognized string.

The pipeline Kanban view copies the incoming nurse array into local `useState` and performs drag-and-drop mutations there. If the parent `NurseDatabase` re-filters or re-sorts (changing the prop), the pipeline will not reflect those changes because `useState(initialNurses)` only seeds state on mount.

Server actions (`actions.ts`) currently log and return `{ success: true }` without persisting anything. The optimistic UI on the pipeline and the next-action dropdown appear to work, but a page refresh will revert all changes to the original mock data.

1. **Divergent scorecard formulas** — `nurse-utils.ts` computes `finalScore` as a raw sum (max ~80) and uses thresholds 70/50 for tiering; `NurseCardDetail.tsx` computes a weighted average (max 10) and uses thresholds 4.0/3.0/2.0/1.0. Either update the type definition to reflect the actual options or align the dropdown to use the existing type values.
3. **Pipeline state diverges from filtered props** — `PipelineView` seeds local state with `useState(initialNurses)` and never re-syncs when the parent passes updated filtered/sorted data. Add a `useEffect` or key the component to reset on filter changes.
4. **No error handling on server action failures** — `handleDragEnd` and `NextActionDropdown.handleChange` perform optimistic updates but don't revert on server action failure (the action currently can't fail, but the pattern is set for future persistence).
5. **`calculateCvScore` operator precedence difference** — In `nurse-utils.ts` the expression `(... / 9 * 5)` groups as `(sum / 9) * 5` due to left-to-right associativity, matching the intent. In `NurseCardDetail.tsx` explicit parentheses `(sum / 9) * 5` make the same calculation but the return value is rounded differently (`Math.min(score, 5)` vs `Math.round(score * 10) / 10`), producing different results for the same nurse.

## Scorecard calculation split

The gallery card calls `calculateCvScore` from `nurse-utils.ts`:

```typescript
// nurse-utils.ts
const score = (hospitalExp * 3 + sancStatusScore * 3 + qualifications * 2 + specialisation * 1) / 9 * 5;
return Math.min(score, 5);
```

The detail card redefines the same function locally:

```typescript
// NurseCardDetail.tsx
const score = ((hospitalExp * 3 + sancStatusScore * 3 + qualifications * 2 + specialisation * 1) / 9) * 5;
return Math.round(score * 10) / 10;
```

These produce different outputs: the utility version clamps at 5.0, while the detail version rounds to one decimal without clamping. More critically, `calculateFinalScore` diverges entirely:

- `nurse-utils.ts`: plain sum of 8 fields (max 80), tiered at 70/50.
- `NurseCardDetail.tsx`: weighted average with different weights (3/3/2/2/1/1/1/2, divisor 15, max ~10), tiered at 4.0/3.0/2.0/1.0.

The gallery uses the utility version for sorting by "CV Score"; the detail page shows the local version. A nurse with `hospitalExp=9, sancStatusScore=10, englishProficiency=9, qualifications=8, specialisation=9, validPassportScore=10, financialReadiness=8, motivationScore=9` gets `finalScore=72` (Tier 1) from the utility but `finalScore=6.2` (Tier 1 Standard) from the detail page. The numbers a user sees on the card won't correlate with the sort order in the gallery, and the tier labels are different systems entirely.

## NextAction type divergence

`types/nurse.ts` defines 22 specific action strings as the `NextAction` union. The mock data uses values from this union (e.g., `"Schedule Check-in"`, `"Register for OET"`). The `NextActionDropdown` component presents 12 completely different options (e.g., `"Needs: Chase CV, then scoring"`, `"Needs: Non-selection email"`). When a user selects a new action from the dropdown, the value written is a string that doesn't exist in the `NextAction` type. This means:

- TypeScript won't catch the mismatch because the dropdown declares its own `const` array and passes the value as a plain `string` to the server action.
- The `getNextActionColor` utility in `nurse-utils.ts`, which matches against `NextAction` values like `"Follow Up Agreement"`, will never match the dropdown's strings and will always fall through to the "upcoming" color.

## Pipeline state isolation

```typescript
export function PipelineView({ nurses: initialNurses }: PipelineViewProps) {
  const [nurses, setNurses] = useState<Nurse[]>(initialNurses);
  ...
}
```

The parent `NurseDatabase` passes `filteredNurses` which changes on every search/filter/sort update. Since `useState` only uses its argument as the initial value, the pipeline continues showing the original unfiltered set after mount. If a user types a name into the search bar while viewing the pipeline, nothing will appear to change.

## Unused Prisma integration

The `prisma.ts` file instantiates the client wrapped in a try-catch (gracefully handling missing generation), but no code path actually queries through it. `getNurses` and `getNurseById` in `data.ts` import directly from `mock-data.ts`. The seed file (`prisma/seed.ts`) duplicates the same 12 nurse records as the mock data module. When the database is eventually connected, either the seed or the mock must be removed to avoid two sources of truth.

## External image URLs without domain allowlist

Gallery cards and the detail view render `<img>` tags with `src={nurse.profilePhoto}` pointing to `api.dicebear.com`. `next.config.mjs` has no `images.remotePatterns` configuration. This works only because raw `<img>` elements bypass Next.js image optimization, which is why an `eslint-disable` comment suppresses the `@next/next/no-img-element` rule. If the team later switches to `next/image` for performance, the build will fail without adding the domain to the allowlist.
