# Help & Onboarding module with knowledge base, wizard, tours, and contextual help

This change adds a complete Help & Onboarding system to the Propela Ops SPA. It introduces a `/help` route with four tabs (Knowledge Base, Onboarding, Feature Tours, Getting Started), a full-screen onboarding wizard that gates new users on first visit, a contextual help popover component, and a multi-step feature tour overlay. State management follows the existing pattern: seed data in `seedHelp.js`, localStorage persistence via `storage.js` helpers, and React context in `AppContext.jsx`. The module is wired into routing, sidebar navigation, and the Layout shell.

**Watch for:** The feature tour spotlight overlay does not actually highlight target elements—it centers a tooltip in the viewport regardless of `target` props in the step config (confirmed). The `highlightText` regex in KnowledgeBase recompiles on every `.test()` call due to the `g` flag, which can produce inconsistent highlighting (confirmed). Tour restart in TourLauncher has a race between updating context (removing from `completedTours`) and mounting a new FeatureTour that immediately reads `isCompleted` (likely).

## High-level view

The onboarding wizard renders as a fixed overlay in Layout.jsx whenever `onboardingState.isComplete` is false. It blocks the entire UI unconditionally—there is no route-aware gating or delay, meaning the overlay fires immediately on any page load for an incomplete user. Progress persists per-step to localStorage, so refreshing mid-flow resumes correctly.

The knowledge base search highlighting uses a regex-split approach with a `g`-flag regex that is then reused for `.test()` calls, causing `lastIndex` drift and inconsistent match detection. Voting is persisted as both a user-vote map and as incremented counts on article objects, creating a dual source of truth that can drift on reseed.

The feature tour system has navigation, persistence, and progress dots, but the "spotlight" interaction is cosmetic only. The tooltip is viewport-centered via CSS transforms, ignoring the `target` selector defined in each step. The `data-tour` attributes from seed data are never queried at runtime.

1. **Spotlight is viewport-centered, not element-targeted** — FeatureTour ignores `step.target`; the tooltip renders at `top:50% left:50%` regardless of which element should be highlighted. Implement `getBoundingClientRect` lookup on `target` selector and position the cutout + tooltip accordingly.

4. **Dual source of truth for article votes** — Vote counts are stored both as fields on article objects (`helpful`/`notHelpful`) and as a separate `articleVotes` map. These can drift if either is modified independently or if seed data resets one but not the other.

## FeatureTour spotlight is decoration-only

The tour overlay in `FeatureTour.jsx` renders a full-viewport dark backdrop (`bg-black/60`) and positions the tooltip at `top-1/2 left-1/2 -translate-x-1/2 -translate-y-1/2`. The `step.target` property (a CSS selector like `[data-tour="pipeline-overview"]`) is defined in seed data but never read at render time. The component receives `steps` as a prop and uses `steps[currentStep]` only for `.title` and `.content`.

Every tour step looks identical from a spatial perspective—the user sees a centered card over a dark wash, with no visual connection to the UI element being described. The feature tour requirements specify "highlight elements with a spotlight effect (dark overlay with cutout)" which is unmet. Implementing this requires querying the DOM for the target element, computing its bounding rect, and rendering a clip-path or box-shadow cutout around it, repositioning the tooltip nearby.

## highlightText regex inconsistency

In `KnowledgeBase.jsx`, the `highlightText` function creates a regex with the `gi` flags, splits the text on it, then tests each part with `regex.test(part)`:

```jsx
const regex = new RegExp(`(${escaped})`, 'gi');
const parts = text.split(regex);
return parts.map((part, i) =>
  regex.test(part) ? (
    <mark ...>{part}</mark>
  ) : (
    <span ...>{part}</span>
  )
);
```

The `g` flag causes `regex.lastIndex` to advance on each `.test()` call, so consecutive matched parts alternate between true and false. For a search query "nurse" in the text "Nurse database for nurse recruitment", the split produces `["", "Nurse", " database for ", "nurse", " recruitment"]`. "Nurse" matches (lastIndex advances to 5), then "nurse" may fail because lastIndex is past position 0 of the new string being tested.

Fix: reset `regex.lastIndex = 0` before each test, or use index parity (after a `split` with a captured group, matched segments always appear at odd indices, making the `.test()` call redundant).

## Tour restart race in TourLauncher

When a completed tour is restarted, `TourLauncher.handleStart` does:
1. `updateTourState(...)` — removes tourId from `completedTours`
2. `setShowTour(true)` — mounts `<FeatureTour>`

The newly mounted FeatureTour computes `isCompleted = tourState?.completedTours?.includes(tourId)`. Since React batches state updates, the context value FeatureTour reads on first render may still contain the old `tourState`. If so, `isCompleted` is true and the component returns null.

A cleaner approach: pass an explicit `active` prop from TourLauncher rather than having FeatureTour derive visibility from context.

## Vote count dual-write

`KnowledgeBase.handleVote` updates two stores: the `articleVotes` map (user's vote keyed by article ID) and the `helpArticles` array (incrementing/decrementing `helpful`/`notHelpful` fields). Both are persisted independently to localStorage. If the app reseeds articles (localStorage cleared for `helpArticles` but not `articleVotes`), the counts reset to seed values while the vote map still records the user's prior vote—the user sees their thumbs-up active but the count doesn't reflect it.

## Tour config duplication

`Help.jsx` defines `TOUR_CONFIGS` with hardcoded step arrays, while `seedHelp.js` defines `featureTours` with the same data plus `target` selectors. The seed data is stored in localStorage but never consumed by the tour UI. Any future update to tour content must be made in two places, and the `target` selectors in seed data serve no runtime purpose.
