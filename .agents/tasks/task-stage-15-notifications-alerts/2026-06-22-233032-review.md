# Notifications & Alerts System Module

This change adds a standalone Notifications & Alerts module at `/notifications` with four tabs: a centralized inbox with read/unread management and date grouping, user-configurable alert rules with severity and delivery channel controls, a toast notification demo system with queue management, and a full notification history with search, filtering, and Recharts analytics. It follows the established pattern of prior modules: page component with tabs, sub-components in `src/components/notifications/`, seed data, localStorage persistence through `storage.js`, and AppContext state.

Watch for: the module overlaps substantially with the existing Communications module's NotificationCenter and AutomatedAlerts components (confirmed); the toast system is demo-only and not wired to actual notification events (confirmed); the NotificationHistory chart will always show zero counts for most days because seed data uses a 30-day random spread against a 14-day chart window (likely).

## High-level view

The module introduces its own storage namespace (`notificationAlerts`, `notifAlertConfig`, `notificationLog`, `toastPreferences`) to avoid colliding with the Communications module's `notifications` and `notificationPreferences` keys. This avoids data corruption but creates two parallel notification systems in the same application — the Communications module already has a NotificationCenter with read/unread management and an AutomatedAlerts configuration panel that handles severity levels, channels, and scheduling.

The toast notification subsystem is entirely self-contained as a demo. It has no connection to the actual notification lifecycle — the `addToast` function is only triggered by a "Trigger Demo Toast" button, not by incoming notifications being created. Toasts never fire in normal usage.

The NotificationHistory component renders a 14-day bar chart from data that spans 30 days of randomly distributed seed entries (60 total). With only ~2 entries per day on average, most bars will show 0 or 1.

Alert configuration uses local component state that only persists on explicit "Save". If the user navigates away from the tab before saving, changes are silently lost.

## Dual notification systems in the same application

The existing Communications module (stage 9) already provides `NotificationCenter` at `/communications` — it manages notifications with read/unread status, type filtering, and delivery preferences. It also provides `AutomatedAlerts` for configuring alert rules with severity, channels, and schedule. The new Notifications module duplicates this functionality with its own data:

```
Communications module:    notifications, notificationPreferences, alertRules, alertHistory
Notifications module:     notificationAlerts, notifAlertConfig, notificationLog, toastPreferences
```

The Sidebar now shows badges on both "Communications" and "Notifications" links, each counting unread items from different stores. From a user's perspective, two red badges counting separate unread pools creates confusion about which inbox is canonical. This should be resolved by either deprecating the Communications notification panel or explicitly scoping each module (e.g., Communications for message history, Notifications for system alerts).

## Toast system isolation

The `ToastNotifications` component maintains its own internal `activeToasts` array via `useState` and `useRef` for timers. The `addToast` function is only called from `handleDemoTrigger`:

```jsx
const handleDemoTrigger = () => {
  const notification = DEMO_NOTIFICATIONS[toastIdRef.current % DEMO_NOTIFICATIONS.length];
  addToast(notification);
};
```

No other component in the application can trigger a toast. The `toastPreferences` stored in AppContext (position, duration, max visible) only affect the demo panel — they're never consumed by a global toast provider. For toasts to work in production, a `ToastProvider` wrapping the app (or exposing `addToast` through context) would be needed.

## History chart UTC/local mismatch

`chartData` counts matching notifications by exact ISO date string:

```jsx
const count = notificationLog.filter((n) => getDateString(n.timestamp) === dateStr).length;
```

`getDateString` uses `toISOString().split('T')[0]`, which converts to UTC. But `generateRelativeTimestamp` in seed data uses `new Date()` (local time) for date arithmetic before calling `.toISOString()`. If the browser is not in UTC, chart dates and seed dates can be shifted by a day, further reducing visible counts beyond the sparsity issue.

## CSV export injection risk

`handleExportCSV` constructs CSV by wrapping each cell in double quotes:

```jsx
const csv = [headers.join(','), ...rows.map((r) => r.map((c) => `"${c}"`).join(','))].join('\n');
```

If any `title` field contains a literal double-quote character, the CSV will be malformed. The standard CSV escape is to double the quote (`""` inside quoted fields). Additionally, formula injection (titles starting with `=`, `+`, `-`, `@`) could be a concern in spreadsheet applications. Minimal fix: `.replace(/"/g, '""')` on each cell value.
